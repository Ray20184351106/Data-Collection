## 1. 结论

可以实现。建议把 CSV 作为现有“可视化字段映射”体系中的一种新输入格式，而不是继续扩展旧脚本页中的 `StreamReader + Split(',')` 示例。

用户侧流程保持与 Excel 基本一致：

1. 选择 CSV 样本。
2. 查看二维表格预览。
3. 选择目标数据模型和记录模式。
4. 点选字段或框选表头与首条数据，生成字段映射。
5. 预览转换后的结果并处理错误。
6. 保存草稿、验证、发布到指定机台。
7. 采集端按“机台 + `.csv`”匹配已发布规则，解析后批量入库。
8. 整个文件入库成功后移入成功目录；任意记录失败则整文件失败，不允许部分成功。

## 2. 当前代码基础与判断

### 2.1 可以直接复用的能力

- `ScriptMatcher` 已按机台和文件扩展名查找已发布规则，数据库绑定结构本身可以承载 `.csv`。
- `ParseRuleStore` 已有草稿、验证、发布、覆盖绑定和版本回退能力，无需为 CSV 新建一套规则表。
- `MappingRuleDefinition`、`FieldMappingRule`、字段转换器、必填校验、模型结构哈希可以继续复用。
- `MappingScriptGenerator` 生成的代码只是调用受控运行时，CSV 不需要让用户或 AI 生成任意 C#。
- `Form1.ProcessFile` 已负责去重、脚本匹配、模型校验、批量入库、错误归档和成功归档。
- 重复行与主子表入库已有文件级事务约束，可以继续用于 CSV 多行数据。
- 现有映射编辑器已有样本网格、点选定位、框选表格、本地辅助、AI 建议、结果预览和机台发布界面。

### 2.2 必须补齐的能力

- `MappingRuleSerializer` 当前只允许 Excel 和图片扩展名，`.csv` 会被拒绝。
- `ExcelMappingPreviewService` 只能读取 `.xls/.xlsx`，运行时和界面也直接依赖该服务。
- 映射界面的样本选择器只接受 Excel 或图片，提示文字、预览行标题也写死为“Excel”。
- 旧脚本页虽然能选择 `.csv`，但示例通过 `Split(',')` 解析，无法安全处理：
  - 双引号包裹的逗号；
  - 双引号转义；
  - 字段内换行；
  - 尾部空字段；
  - UTF-8 BOM、无 BOM UTF-8、GBK/GB18030 等编码；
  - 列数不一致、重复表头和超大文件。
- `FileParser.ParseCsv` 也使用简单分割，而且当前仅被 `Form1` 声明、未进入实际采集链路，不能作为新功能基础。

### 2.3 当前限制

当前发布绑定的唯一维度是“机台 + 扩展名”。因此同一机台默认只能启用一条 `.csv` 规则。如果同一机台会产生多种结构不同的 CSV，需要另行增加内容签名路由；这不是简单增加扩展名即可解决的问题。

## 3. 首版范围建议

### 3.1 默认纳入

- 文件扩展名：`.csv`，大小写统一归一为小写。
- 格式：标准带表头 CSV。
- 记录模式：
  - 单条记录：表头下一行生成一条模型记录；
  - 重复行：表头后多行生成多条同模型记录；
  - 主表 + 子表：主表字段来自文件名，CSV 各数据行生成子表记录。
- 分隔符：默认逗号；界面可明确选择逗号、分号、Tab、竖线，不依赖不透明的自动猜测。
- 引号：默认双引号，正确支持引号内分隔符、换行和 `""` 转义。
- 编码：
  - 默认使用严格 UTF-8，并接受与所选编码一致的 UTF-8 BOM；
  - 非 UTF-8 文件要求用户明确选择 GB18030/GBK；
  - 最终选择写入规则，运行时不得再次猜测；BOM 与所选编码冲突时明确失败。
- 空白行：可跳过；空字段保留为空，不允许因空字段导致后续列错位。
- 异常行：默认整文件失败，报告源文件行号、列号和目标字段，不静默截断。
- 文件上限沿用现有 Excel 安全边界：20 MiB、最多 2,000 个逻辑行（含说明、表头和数据行）、128 列、20,000 个非空单元格、单字段显示文本最多 2,048 字符。
- 转换能力沿用现有白名单：去空格、空白归一、整数、小数、日期、精确值映射和默认值。

### 3.2 首版不纳入

- 无表头 CSV 的自动推断。
- 一个 CSV 文件生成多个无关联目标模型。
- 跨多个 CSV 文件聚合后再入库。
- AI 直接生成或执行 C# 解析代码。
- 自动创建业务模型或业务表。
- 同机台多种 CSV 模板自动路由，除非需求确认确实存在。
- 修改 Center/Agent 的集中映射分发范围；当前计划只覆盖 WinForms 本地字段映射链路。

## 4. 需要确认的业务问题

实施前需要用 2～3 份真实设备 CSV 样本确认以下内容：

1. 文件实际编码是 UTF-8、GBK/GB18030，还是多种编码并存。
2. 分隔符是否始终为逗号，字段中是否存在逗号、双引号或换行。
3. 表头是否固定在第一行，前面是否还有设备说明、批次信息或空行。
4. 一份文件通常包含一条还是多条数据，是否需要“主表 + 子表”。
5. 同一机台是否可能输出两种以上结构不同的 `.csv` 文件。
6. 遇到某一行错误时，是否接受“整文件失败”的默认策略。
7. 2,000 个逻辑行/文件的现有限制是否覆盖设备最大输出量。

在这些答案缺失时，本计划按“固定表头、每机台一种 CSV 模板、整文件原子失败”推进。

## 5. 技术方案

### 5.1 总体链路

```text
CSV 样本
  -> CSV 安全读取与结构校验
  -> 转换为通用二维样本快照
  -> 复用现有可视化映射编辑器
  -> 生成受约束的 DefinitionJson
  -> 预览、验证、保存草稿、发布到机台
  -> ScriptMatcher 按机台 + .csv 匹配
  -> MappingRuntime 按扩展名分派到 CSV 预览/解析器
  -> 生成单条、多条或主子表模型
  -> 文件级事务入库
  -> 成功/失败目录
```

### 5.2 核心设计决定

#### A. 记录模式与文件格式分离

不新增 `CsvRecordMode`。`SingleRecord`、`RepeatingRows`、`MasterDetail` 继续表达“生成多少条、是否主子表”；`.csv` 和 CSV 选项表达“如何读取源文件”。这样可以避免复制 Excel 的整套规则模型。

#### B. 按扩展名进行预览分派

`MappingRuntime` 和映射界面根据已验证的规则扩展名选择 Excel、CSV 或图片服务。CSV 服务把严格解析后的快照写入临时虚拟工作簿，再调用 Excel 映射核心的内部入口；这样避免复制字段定位、转换、重复行和主子表逻辑，同时保证普通 Excel 仍走原入口和原有语义。

#### C. CSV 转换为“虚拟工作表”

CSV 读取后转换为一个名为 `CSV` 的虚拟工作表和二维单元格快照，坐标仍采用 `A1`、`B1`、`A2`。这样可继续复用样本网格、点选、框选表头、字段转换和结果预览。

CSV 没有合并单元格和公式，相关 Excel 专有信息保持为空；界面只显示与当前格式相关的控件。

#### D. 规则中保存明确的 CSV 选项

建议在 `MappingRuleDefinition` 增加可空的 `CsvOptions`：

- `EncodingName`
- `Delimiter`
- `QuoteCharacter`
- `HeaderRowNumber`
- `FirstDataRowNumber`
- `SkipBlankRows`

Excel 和图片规则的 `CsvOptions` 必须为空；CSV 规则必须存在并通过白名单校验。

#### E. 历史规则哈希必须兼容

新增可空属性可能改变现有 Excel/图片 `DefinitionJson` 的规范化结果，进而让已发布规则的 SHA-256 完整性校验失败。实现时必须保证：

- `CsvOptions == null` 时不改变旧规则的规范 JSON；
- 使用真实历史 Excel/图片规则 JSON 做反序列化、再序列化和哈希回归；
- 不通过“关闭完整性校验”来兼容旧数据。

#### F. CSV 解析器选择

禁止自行用 `Split(',')` 代替 CSV 解析器。优先评估兼容 .NET Framework 4.8 的成熟 CSV 库；新增依赖前确认内部源、许可证和发布包体积。如果不允许新增依赖，可使用框架能力实现，但必须通过同一组引号、换行、编码和畸形数据测试。

CSV 没有可靠的 magic bytes，不能像 Excel 一样做文件头签名校验；应以扩展名、大小、严格解码、完整 CSV 语法和行列结构校验共同作为边界。

#### G. 模板签名

CSV 模板签名建议由以下内容组成：

- 归一化后的表头顺序；
- 分隔符、引号字符、编码名；
- 表头行号和首数据行号；
- 重复行关键列和已映射列；
- 必填的固定锚点。

普通数据值不进入模板签名，避免每个文件内容变化都导致模板不匹配。

#### H. 旧 CSV 脚本兼容

已有手写 CSV 脚本继续保留并可运行，不自动迁移、不删除。新可视化 CSV 映射使用 `RuleJson/DefinitionJson -> 固定生成器 -> MappingRuntime` 链路。旧 `FileParser.ParseCsv` 的清理作为单独技术债处理，不与本功能绑定。

## 8. 测试矩阵

| 类别 | 必测场景 | 预期 |
|---|---|---|
| CSV 语法 | 普通逗号、引号内逗号、`""`、字段内换行、尾空字段 | 值和列位置正确 |
| 换行 | CRLF、LF、文件末尾无换行 | 记录数一致 |

## 10. 风险与应对

| 风险 | 等级 | 应对 |
|---|---:|---|
| 同机台存在多种 CSV 模板，当前只能按扩展名匹配 | 高 | 实施前确认；需要时另立“内容签名路由”任务 |
| 简单字符串分割导致字段错位 | 高 | 使用正式 CSV 解析器和复杂字段回归测试 |
| 编码误判造成中文乱码或错误入库 | 高 | 自动模式仅限可验证编码；非 UTF-8 明确选择并持久化 |
| 新规则属性使历史 Excel/图片哈希失效 | 高 | 属性条件序列化 + 真实历史 JSON 哈希回归 |
| 单行错误导致部分数据已写入 | 高 | 文件级事务、失败回滚、目标表回读验证 |
| 超大或畸形 CSV 消耗过多内存/CPU | 中 | 流式解析、大小/行/列/字段上限、及时终止 |
| UI 仍显示 Excel 专用概念，用户误配 | 中 | 动态格式提示、CSV 虚拟工作表、通用“源文件行”文案 |
| 新增第三方库影响许可或离线发布 | 中 | 依赖评审门槛；保留框架实现备选，不自行简化协议 |
| 只通过单元测试但现场目录/账户/数据库不同 | 中 | 分层记录证据，必须完成部署与真实样本试点 |

## 11. 质量与安全边界

### 始终执行

- 所有 CSV 内容都视为不可信输入。
- 校验路径、扩展名、大小、编码、CSV 语法、行列和字段长度。
- 规则仅保存声明式 JSON，生成代码由固定生成器产生。
- 数据库继续通过现有参数化 ORM/事务路径写入。
- 保留失败文件和可定位的错误信息，不记录数据库凭据。
- 修改前后检查 Git 状态，保护用户未提交内容。
- 构建、测试、部署、现场验证分别陈述证据等级。

### 实施前需确认

- 新增第三方 CSV 依赖。
- 同机台多模板路由。
- 修改现有限制值。
- 目标数据库表结构变更。
- 生产环境部署或生产数据库写入。

### 不执行

- 不使用 `Split(',')` 作为正式解析器。
- 不让 AI 输出并直接执行任意代码。
- 不因兼容问题关闭规则完整性校验。
- 不在错误行出现时静默丢行或截断列。
- 不自动覆盖现有 Excel、图片或旧脚本绑定。
- 不把本地测试通过描述成现场生产验证通过。

## 13. 完成标准

同时满足以下条件才算功能完成：

1. 用户能从真实 CSV 样本完成“选择、映射、预览、保存、验证、发布”。
2. 复杂 CSV 字段、中文编码和空字段解析正确，不发生列错位。
3. 单条、重复行及已确认需要的主子表模式按预期生成模型。
4. 采集端能按目标机台匹配 `.csv` 规则并完成文件级原子入库。
5. 任意行失败时数据库无部分记录，文件进入错误目录并提供可定位错误。
6. 已发布 Excel、图片和旧脚本规则完整性校验及运行结果不受影响。
7. CSV 定向测试、采集端完整测试和 Release 隔离构建通过。
8. 在获得部署授权后，用真实设备样本完成目标数据库回读和目录归档验收。
